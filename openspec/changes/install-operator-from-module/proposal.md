## Why

`opm operator install` applies a manifest compiled into the CLI (`internal/operator/dist/install.yaml`, pinned by `PinnedOperatorVersion` in `internal/operator/manifest.go:19`). Nothing records what it installed, every reinstall force-applies the manifest and drops whatever a team patched onto the Deployment (the operator's install guide documents this trap for `--registry`), and uninstall deletes the CLI's list of objects instead of what the cluster holds.

The opm-operator repository now publishes the operator as an OPM module, `opmodel.dev/modules/opm_operator`, on a version train of its own. OPM should install its own operator the way it installs everything else: as a ModuleInstance whose record and inventory say what is there. The operator's own instance stays CLI-owned for good; the operator never reconciles the instance that deploys it, so re-running the CLI is always the recovery path.

A hand-run experiment on 2026-10-04 performed that install, reinstall, upgrade and delete on a kind cluster with a published copy of the module (measurements in design.md, "Evidence"). The two-step install worked, but it found what the CLI must add: a refused install had already relabelled the CRDs, `opm instance apply --wait` returned about 30 s before the new operator reconciled anything, `--create-namespace` collides with the Namespace the module renders, and the second install rendered through the cluster Platform instead of the module's own pins. This change makes `opm operator install` perform that install itself, with the refusals and the wait it needs.

## What Changes

- **BREAKING: install deploys the operator module.** `opm operator install` pulls `opmodel.dev/modules/opm_operator` from the configured registry, renders it against the module's own dependency pins, runs every check that can refuse, then applies the module's CRDs (server-side, field manager `opm-cli`, wait `Established`) and then a CLI-owned ModuleInstance `opm-operator` in `opm-operator-system` through the ordinary instance apply. It never creates the Namespace itself: the module renders it. Install needs a module registry, or a mirror of one, where the embedded manifest needed none. There is no embedded fallback; an air-gapped cluster installs from a mirror through the CLI's registry mapping.
- **Every refusing check runs before the first write**: the content-digest check of the default version, the recorded values against the target version's `#config`, no operator newer than the CLI (`MAJOR.MINOR`), no downgrade unless asked for, no CRD that stops serving a version the cluster serves, no ModuleInstance CRD below the CLI's floor, and the apply guard over every rendered object. The running-operator ceiling (0021:D9) no longer refuses the operator's own install, because install replaces that operator; the target check takes its place.
- **Success means the new operator is reconciling.** Install waits for the Deployment rollout and then for the cluster Platform to report Ready from the operator release just installed; on timeout it keeps what it applied and names the Platform and its condition.
- **BREAKING: `--version` selects a module version**, resolved through the registry, instead of an opm-operator release tag fetched from GitHub. A version other than the default is reported as trusted as the registry serves it.
- **The CLI pins a default module version, the content digests of the module and of every module its render resolves, and the operator version that module deploys**, generated by a new `task operator:pin VERSION=<v>`. This replaces the embedded `dist/install.yaml`, `task operator:sync`, the GitHub fetch (`internal/operator/fetch.go`) and the release-pin check's image-tag comparison. The constant `PinnedOperatorVersion` stays, now meaning the operator version the pinned module deploys, so the docs pins (`hack/docskit-dump`) and the release evidence check keep reading it offline.
- **New flags:** `-f/--values` (repeatable) layers values files over the values recorded on the operator's instance; `--reset-values` starts from the module's defaults instead; `--allow-downgrade` permits an explicit downgrade. A reinstall keeps every recorded value the run does not change.
- **`--crds-only`** applies exactly the CRDs of the same render, writes no record, workload or Platform, and refuses under the version and CRD rules that concern CRDs. It now needs the registry.
- **Platform seeding and `--rbac` stay install steps, unchanged** (0006:D12, 0006:D22, 0006:D23); neither the Platform nor the user role enters the operator's inventory.
- **BREAKING: uninstall deletes the operator instance's recorded inventory**, except CRDs and the Namespace, then the record, under the existing finalizer guard (0006:D34); with no record it deletes nothing and names install. Upgrade prunes what the new version no longer renders.
- **Tooling follows:** `task cluster:operator` passes the local registry as an instance value instead of patching the Deployment; the e2e lifecycle test, the e2e cluster job, the release-pin check (G1), the operator evidence check (G4), the cascade's operator lane and the docs pins key on the pinned module.

## Dependencies / gates

**GATED.** Implementation starts only when both hold; task 1.1 checks them and stops with a report if either fails.

1. **The first operator module release is published on GHCR**: opm-operator's `add-operator-module` and `release-operator-module` merged and released, so `opmodel.dev/modules/opm_operator` holds a `v0.x.y` that names a published operator image by tag and digest and renders through the catalog_opm release that adds the pod seccomp profile and subject-less roles (`add-seccomp-and-subjectless-roles`).
2. **`locate-operator-and-guard-its-instance` is merged** on cli `main`: it supplies the running-operator locator (instance record first, fixed names otherwise), the fixed names in `internal/operator/names.go`, and the finalizer guard on `opm instance delete` of the operator's instance, all of which this change relies on.

**Release coupling (not a merge gate; supervisor decision).** `migrate-manifest-installed-operator`, the first module install over an operator applied from a manifest, is gated on this change. Between the two, `opm operator install` on such a cluster refuses at the apply guard (the experiment measured exactly this, design.md "Evidence", step 6). A cli release cut in that window would ship an install that refuses on every existing cluster. The refusal names the earlier operator as the cause and changes nothing; whether the owner holds cli releases for that window or the two changes ship in one PR is the supervisor's call.

Local cluster note: the kind cluster `opm-dev` and the containers on the host that planned this change have no internet egress, so cluster e2e cannot run there. Unit and integration tests are the bar for the PR, and the PR says so; the e2e cluster job in CI is the cluster evidence.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `operator-lifecycle`: install, CRDs-only install, `--version`, the pin and uninstall move from the embedded manifest to the operator module and its CLI-owned instance; new refusal, values and readiness requirements.
- `platform-resolution`: operator install renders against the operator module's own pins and never reads the cluster Platform.
- `apply-preflight-gates`: the running-operator ceiling does not refuse the operator's own install.
- `release-gates`: G1 checks the pinned module, its digests and its recorded operator version; G4 keys on the pinned module version.
- `docs-bundle`: the `opm-operator` pin is the operator version recorded beside the pinned module.
- `deps-cascade`: the operator lane moves the module pin through `task operator:pin`.
- `e2e-cluster-workflow`: the job installs the pinned operator module, not an embedded manifest.
- `kind-cluster-tasks`: the local-registry opt-in sets the operator's registry as an instance value.

## Impact

- **Release class: MAJOR after GA** (install needs a registry, `--version` changes meaning, uninstall deletes from the record). On the beta line it ships as the next `beta.N` with a `feat!` title and a migration note.
- **Commands:** `opm operator install`, `opm operator uninstall`.
- **Packages:** `internal/operator` (install, uninstall, plan, pin, verify; `manifest.go`, `fetch.go` and `dist/` deleted), `internal/cmd/operator`, `internal/workflow/apply` (ceiling exemption option, shared instance delete), `internal/workflow/render` (explicit values source, deps-only platform for install), `internal/inventory` (CRD floor over an unstructured CRD), `hack/docskit-dump`, new `hack/operator-pin`.
- **Tooling:** `Taskfile.yml` (`operator:pin` replaces `operator:sync`; `cluster:operator`), `.github/scripts/release-pin-check.sh`, `.github/scripts/release-evidence.sh`, `.tasks/cascade/`, `.github/scripts/e2e-cluster-applies.sh`, `tests/e2e/operator_test.go`.
- **Docs:** `README.md` operator section, `AGENTS.md`, command help. The install pages in `opm` and `opm-operator` are those repos' changes.
- **Library dependency (decided in section 1):** the digest-anchored render needs kernel loads confined to a private CUE cache directory. The kernel exposes no cache-directory option at library `v1.0.0-beta.3`; section 1 decides between a library option and a CLI-side override and reports before section 2 if a library release is needed.
- **Out of scope:** the migration of a manifest-installed operator (`migrate-manifest-installed-operator`); the operator module itself, its `#config` and its release train (opm-operator); the catalog additions (catalog_opm); the workspace release rules and cascade receiver for the module train; and any transfer of the operator instance's ownership (it stays CLI-owned; no command here changes its owner).
