## Context

`opm controller install` resolves the controller module `opmodel.dev/modules/opm_controller` through the registry,
renders it as the instance `opm-controller` in `opm-controller-system` against the module's own dependency pins, and
applies the render's CRDs before the instance. `--crds-only` stops after the CRD step, but it still resolves, fetches and
renders the module (catalogs included) and reads the controller's instance record for recorded values. The pin task
(`hack/controller-pin`) writes `internal/controller/pin.go` from the module's controller package without a render.

The offline installer runs `opm controller install --crds-only` with no network beyond the API server, which today
fails at the module resolve.

## Goals / Non-Goals

**Goals:**

- `--crds-only` needs only the Kubernetes API server.
- The objects it applies are the objects the online CRD step applies for the pinned version, byte for byte, so a later
  full install records them without recreating them, and its apply guard accepts them.
- One reviewable diff per re-pin: the pin file and the manifests move together, and G1 catches drift.

**Non-Goals:**

- Offline full install, offline `--version`, or bundling the module source in the binary.
- Changing what a full install renders, checks or writes.

## Decisions

### C1: The manifests are the pinned version's rendered CRDs, not controller-gen's files

The pin task renders the module version exactly as install renders it (the same `ModuleOpts`: instance name and
namespace, no values, deps-only) and keeps the `CustomResourceDefinition` objects. These carry the instance labels
(`app.kubernetes.io/managed-by: opm-cli`, the module and instance identity), which the controller repository's
`config/crd/bases` files do not. With those labels:

- the apply guard of a later full install accepts the existing CRDs as OPM's;
- the CRDs-only and full CRD steps apply the same objects, so 0021:D11:R7 ("the CRDs-only form applies only the CRDs of
  the same render the full install applies") still holds for the pinned version.

The alternative, embedding `config/crd/bases` and adding labels at apply time, keeps a second copy of the label set in
the CLI that drifts from the render. It was rejected.

The CRDs do not depend on values: the module's `crds` component reads only its generated `#crdSource`. The render
passes no values, as a fresh install with no record does.

### C2: One generated YAML file per CRD, embedded

The manifests are written as `internal/controller/crds/<crd name>.yaml`. Each file holds one object serialised with
`sigs.k8s.io/yaml`, which sorts keys, under a `# Code generated by task controller:pin; DO NOT EDIT.` header. A re-pin
first removes every `*.yaml` in the directory, so a CRD the module drops disappears. Package `crds` embeds `*.yaml` and
returns the objects in file-name order. Deterministic bytes make the cutover re-pin and the G1 check exact comparisons.

### C3: `--crds-only` installs the pinned version only

`--version` with `--crds-only` is a flag-validation error (exit 2) that names the pinned module version. Fetching the
module when `--version` is given would put a registry back on a path the offline installer depends on, and give one
flag two behaviours. `-f/--values` and `--reset-values` stay refused as before.

### C4: The offline plan guards the CRDs without reading the record

The CRDs-only plan reads no ModuleInstance, so it cannot know whether a record exists. It waits out terminating CRDs
within `--timeout`, then runs the apply guard over the embedded CRDs every time: a CRD that exists and is not labelled
as OPM-managed refuses the install (exit 2, nothing applied). CRDs a previous install applied carry OPM's managed-by
label and pass. It runs no target rules: the controller-version, image and CRD-floor rules judge a module version that
the pin already judged. A unit test holds the embedded ModuleInstance CRD to the CLI's field floor and its labels to the
pinned version.

The plan also reads the existing CRDs from the API server and refuses (exit 2, nothing applied) when one carries a
`module.opmodel.dev/version` label newer than the pinned module version: a full install of that version, made with
`--version`, recorded those CRDs, and applying the pin's older schemas under the controller it deployed would be a
silent downgrade. The refusal names the full install of that version as the remedy. Accepting the downgrade as a
limitation was rejected, since before this change `--crds-only --version X` could match the installed version and that
escape is gone. The read reaches only the API server, so the form stays offline.

### C5: Render options live in `internal/controller`

`ModuleRenderOpts` moves from the command into `internal/controller`, and both install and the pin task call it, so the
pin cannot render the module differently from install.

### C6: The pin check renders, and a local bootstrap exists

`--check` renders the pinned version, with the render's logs discarded, and compares the bytes it would write with the
embedded files, reporting each missing, extra or differing file with the `task controller:pin VERSION=<v>` fix. A
render failure is a failure to check, never a pass.

`--crds-from <module-dir>` renders a local checkout instead of a published version and writes only the manifests. It
exists for the window before a module version is published (this change was bootstrapped from the controller
repository's rename branch). The re-pin against the published version must then produce no diff.

## Risks / Trade-offs

- **The binary carries CRDs that can disagree with what `--version` installs.** Mitigation: `--crds-only` refuses
  `--version`, and a full install of another version applies its own rendered CRDs over them.
- **The cascade's controller-module lane writes more files.** The cascade runs the pin program built from the merge
  base, so a cascade PR that moves the module also moves the manifests. Unlisted paths are classed `shipped`, which is
  right for embedded files.
- **G1 now renders the module**, so it needs the module's catalogs from the registry. G1 already reaches the registry
  for the pin lookup.
