## Why

`opm controller install --crds-only` renders the controller module to get its CustomResourceDefinitions, so it needs the
registry that serves the module and its catalogs, and it reads the controller's ModuleInstance record first. A
CRDs-only install is the bootstrap for clusters where the CLI drives module lifecycle without a running controller, and
the offline installer (opm-suite-installer) runs it under a no-network rule: there it cannot reach a registry at all.
The owner decided on 2026-10-06 that the CRDs-only form works fully offline from CRDs the CLI carries, pinned with the
controller module, while every other install path stays module-based. Enhancement 0021 records it as revised
0021:D11:R1 and 0021:D11:R7 (revised 2026-10-06).

## What Changes

- `task controller:pin VERSION=<v>` also renders the module version as install renders the controller's instance and
  writes that render's CRDs as manifests under `internal/controller/crds/`, which the CLI embeds.
- `opm controller install --crds-only` applies the embedded CRDs with server-side apply as `opm-cli` and waits for
  `Established`. It makes no registry request and renders nothing. It reads the record of the controller's instance
  when one exists, for its inventory only, and writes no ModuleInstance. Its only network peer is the Kubernetes API
  server.
- `--crds-only` judges every existing CRD with the shared apply guard, as a full install does: a CRD the record lists
  is applied; a CRD without OPM's managed-by label, or with another instance's identity, is refused with exit 2 before
  any write, and the refusal prints the `opmodel.dev/adopt` annotation to set. It adopts nothing by itself. It also
  refuses CRDs a newer version of the controller module installed, naming both remedies: `--crds-only` from a CLI that pins that
  version or newer, or a full install of that version.
- **BREAKING**: `--crds-only` refuses `--version` as a flag-validation error. It installs only the CRDs of the module
  version this CLI pins.
- The pin check (`go run ./hack/controller-pin --check`, part of G1) also fails when the embedded manifests differ from
  a fresh render of the pinned module version.
- The pin tool gains `--crds-from <module-dir>`, which writes the manifests from a local checkout of the controller
  module before that version is published. It never touches the pin file.
- Full install, `--version`, values and the Platform seed are unchanged and stay module-based.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `controller-lifecycle`: the CRDs-only requirement is replaced by an offline one; the pin requirement also covers the
  embedded CRD manifests and their check; the refusing-checks requirement names the CRDs-only form's own checks.
- `platform-resolution`: the controller install's deps-only render applies to the full install; the CRDs-only form
  renders nothing at install time.

## Impact

- New package `internal/controller/crds` (embedded manifests, generated by the pin task).
- `internal/controller`: an offline CRDs-only plan; the module render options move here from the command, so the pin
  task and install render the module the same way.
- `internal/cmd/controller/install.go`: the CRDs-only path skips the registry and the catalog lookup.
- `hack/controller-pin`: renders and writes the manifests, checks them, and `--crds-from` bootstraps them from a
  directory.
- `.github/workflows/pr.yml`'s integration job keeps running `opm controller install --crds-only`; it now needs no
  registry for that step.
- Delivers the cli side of 0021:D11:R1/R7 (revised 2026-10-06): the CLI carries no controller manifest beyond the CRDs
  of its pinned module version, and the CRDs-only form applies them without a registry or the controller's instance.
  `enhancement.yaml` declares 0021 with no decisions, since D11 was claimed by install-operator-from-module. The
  change depends on the revised 0021:D11 reaching enhancements main.
