## Context

opmodel.dev assembles its pages from every source repository's `docs/site/` in the page dialect (workspace `STYLE.md`, "Site Pages"), lints them (`site/scripts/lint-sources.sh`) and fails the build on a broken link. The cli's command tree is built by `internal/cmd.NewRootCmd`; every command carries `Use`, `Short` and `Long`, several carry `Aliases`, and none sets cobra's `Example` field: the examples are written inside `Long`, under an `Examples:` line. `Long` strings are raw Go strings, so their lines carry the indentation of the Go source that declares them (none, one tab or two tabs, sometimes mixed within one string).

## Goals / Non-Goals

**Goals**

- Every visible command, its usage, description, flags and examples on the site, in the dialect, generated from the command tree and nothing else.
- A check that fails locally (`task check`) and in CI when the committed pages are stale.
- Output that is byte-identical across machines and runs.

**Non-Goals**

- Rewording any help text. The generator reformats; it never adds a fact the command tree does not hold. Help-text problems it surfaces are fixed in the commands, then regenerated.
- Man pages or other formats.

## Decisions

### 1. One page per top-level command, one entry per command

Command syntax: `go run ./hack/cmdref [-check] [-dir docs/site/reference/cli]`.

The section page `_index.md` holds the root's description, its usage and the global flags (the root's persistent flags) once. Each top-level command gets `opm-<name>.md`, `type: reference`, with an entry (`## opm module apply`) for the command and every visible command under it, depth first in name order. A top-level command with no subcommands, such as `opm version`, is a page with one entry, so every page has the same shape.

Every entry has the same parts in the same order, each only when the command has it: summary (`Short`), usage (a `text` fence mirroring cobra's usage template, then the aliases), description (`Long` minus its examples), flags (a table of name, shorthand, type, default and description), examples (an `sh` fence), subcommands (a table linking each child's entry). Parts after the usage are introduced by a bold label rather than a heading, so the page's table of contents (levels 2 and 3) lists commands, not dozens of "Flags" headings.

A flag table lists a command's own flags and any flag a non-root parent makes persistent; global flags are listed once on the section page, and each command page links there. Hidden flags, deprecated flags and cobra's `--help` are left out. A default is shown only where `--help` shows one (not for `""`, `false`, `[]`, `0`, `0s`), and the user's home directory in a default is written `~`.

### 2. A parser for `Long`, not a verbatim fence

`Long` is split into paragraphs. The base indentation is the shallowest first line of any paragraph after the first; a line indented beyond it is preformatted, a line at it is prose, and the first paragraph is always prose. Consecutive preformatted lines become one fence (`sh` when every line is an `opm` command or a comment, `text` otherwise); prose lines are joined into one paragraph. A prose line reading `Examples:` starts the examples, which run to the next prose line.

Prose is escaped for Markdown. Words that name code, namely flags, paths, placeholders (`<dir>`), environment variables, CUE definitions (`#config`), file names and single-quoted commands (`'opm module vet'`), become code spans, so the site never reads them as markup, raw HTML (the site renders with `unsafe = true`) or autolinks. The words are unchanged. Hugo expands `{{<` even inside fences, so shortcode delimiters are escaped as `{{</* ... */>}}`.

### 3. Marker comments and the authored remainder

The generator owns the front matter and the block between `<!-- generated by task docs:reference from the opm cobra commands; DO NOT EDIT -->` and `<!-- end generated -->`. Text between the front matter and the begin marker, and after the end marker, is kept on regeneration. A `.md` file in the directory without the marker is authored and never touched; one with the marker that no command produces any more is removed by `docs:reference` and reported by the check. A page that has lost its markers is an error, never overwritten.

### 4. The check is the generator in `-check` mode

`-check` renders in memory, composes each page with the authored parts of the file on disk and compares bytes. It prints `stale: <path>` for each difference and exits 1 with the remedy (`run task docs:reference and commit the result`). `task check` runs it before the tests; CI runs it as its own job in `pr.yml` and `ci.yml`, so the failure names itself.

### Errors

| Condition | Result |
| --- | --- |
| A page is stale, missing or orphaned (`-check`) | exit 1, one `stale:` line per file |
| A generated page lost its front matter or markers | exit 1 naming the file and what is missing; nothing written |
| A top-level command name is not kebab-case | exit 1 naming the command |

## Research & Decisions

### Renderer

**Context**: cobra ships `cobra/doc`, which can write Markdown.
**Explored**: `doc.GenMarkdownTree` output for this tree.
**Options considered**:

1. `GenMarkdownTree` plus post-processing - one file per command with relative `.md` links and untagged fences; rewriting links and fences after the fact is a second parser of cobra's Markdown and still yields 40-odd pages.
2. Own renderer over the command tree - full control of layout and escaping; about 850 lines of Go without tests.

**Decision**: own renderer.
**Rationale**: the dialect rules are the hard part, and they are easier to satisfy by construction than by repair.

### Where the examples come from

**Context**: no command sets `Example`; every example is inside `Long`.
**Options considered**:

1. Show `Long` verbatim, examples included - faithful, but an `Examples:` label inside a `text` fence loses the `sh` tag and the fixed part order.
2. Split the `Examples:` block out of `Long` - the same text, in the examples part.

**Decision**: split it, and append cobra's `Example` field when a command sets one.
**Rationale**: keeps one entry shape without changing the help text.

### The completion command

**Context**: cobra adds `completion` when the CLI executes, not in `NewRootCmd`.
**Decision**: the generator calls `InitDefaultCompletionCmd` before rendering, so the reference lists what `opm --help` lists. The `help` command is left out, as cobra marks it unavailable.

## Risks / Trade-offs

- **The prose formatter is heuristic.** It decides which words are code. A misjudged word renders as a code span or as escaped text, never as a wrong fact; the committed pages are reviewed as a diff in every PR that changes help text.
- **Help-text quirks surface on the site.** Three `Long` texts carry enhancement citations (`0011:D25`, `0015:D5`, a bare `D20`) that the cli's comment rules keep out of CLI output; the reference reproduces them until the commands are fixed. cobra's completion help carries `#### Linux:` lines, which render as literal text.
- **Order of rollout.** Until opmodel.dev drops its placeholder and its RESERVED check, a site build that includes this branch fails with both sources publishing `/docs/reference/cli/`. Merging this before the opmodel.dev change makes the site's next build fail; merge after it, or together.

## Migration Plan

Regenerate with `task docs:reference` whenever a command's `Use`, `Short`, `Long`, `Example`, `Aliases` or flags change; the check fails CI otherwise. Rollback is reverting the commits; nothing in the binary depends on them.
